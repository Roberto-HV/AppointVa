Punto de Venta

Sistema instalable en desktop y móvil nativo. Offline-first con sync a la nube. Integración con AppointVa como diferenciador principal.

Turborepo · Expo · Electron · PowerSync · Supabase shadcn/ui + NativeWind TypeScript end-to-end

Decisión de plataforma

El requerimiento de instalación nativa en móvil cambia el juego. Electron no corre en iOS ni Android. Hay dos caminos reales.

Recomendación — Path A

Monorepo Turborepo con Expo (React Native) para móvil + Electron para desktop. Compartes el 60–65% del código: business logic, tipos, estado, API client, sync. Cada plataforma tiene su capa de UI y su capa de acceso a hardware. Aprovechas React y TypeScript que ya dominas. Tiempo a MVP es el más corto de todas las opciones.

Por qué no PWA ni Capacitor

iOS Safari no implementa WebUSB ni Web Serial y Apple no tiene planes de hacerlo. Sin esas APIs no hay acceso a impresoras térmicas USB ni a puertos serie desde el navegador. En Android existe soporte parcial, pero no en iOS — y no puedes lanzar un POS que funcione solo en la mitad de los teléfonos.

Stack definitivo

Gestión del monorepo

Turborepo — builds incrementales cacheados, pipeline de tareas paralelas entre workspaces. Con pnpm workspaces como package manager (más eficiente en espacio en disco que npm/yarn para monorepos).

App desktop

Electron 33 + React 19 + TypeScript + electron-vite. El proceso main maneja SQLite, servidor Express para terminales locales, sync con PowerSync, y drivers de impresora. El renderer es React puro con shadcn/ui.

App móvil

Expo SDK 53 + React Native + TypeScript. Expo provee el toolchain completo: EAS Build para compilar .ipa y .apk sin Mac en CI, Expo Router para navegación, OTA updates para desplegar sin pasar por la App Store. La UI usa NativeWind v4 — Tailwind CSS sobre primitivas nativas. Componentes complejos de UI de POS (carrito, teclado numérico, producto grid) se construyen custom.

Base de datos local

better-sqlite3 en desktop (síncrono, ideal para Electron). expo-sqlite en móvil (SQLite nativo en iOS/Android). El schema es idéntico en ambas plataformas — definido en el paquete compartido packages/db-schema con Drizzle ORM.

Sync offline-first

PowerSync + Supabase. PowerSync sincroniza un subconjunto de Supabase Postgres a SQLite local por dispositivo. Las lecturas son siempre locales. Las escrituras van a una cola de upload local y se sincronizan cuando hay red. Reemplaza por completo el sync_queue manual — PowerSync lo maneja con reintentos, conflictos y estado visible.

Cloud backend

Supabase — Postgres + Auth + Realtime + Storage. El tier gratuito cubre proyectos iniciales. Auth maneja sesiones de cajero via JWT con RLS (Row Level Security) — cada negocio solo ve sus propios datos.

UI

shadcn/ui + Tailwind v4 en desktop. NativeWind v4 + componentes propios en móvil. La lógica compartida (custom hooks, estado de carrito, cálculos de pago) vive en packages/core y la consumen ambas plataformas.

Estado global

Zustand — el store de carrito, sesión de caja, cajero activo. Sin boilerplate, funciona igual en Electron renderer y React Native. No usar Context API para estado de alta frecuencia (actualizaciones del carrito) — Zustand es más eficiente.

Estructura del monorepo

Todo el código vive en un solo repositorio. Cambias un tipo en packages/db-schema y TypeScript te señala al instante dónde falta actualizar en desktop y móvil.

Qué se comparte vs qué es específico de plataforma

Compartido (packages/): tipos del DB schema, lógica de cálculo de carrito y pagos, stores de Zustand, cliente de Supabase/PowerSync, formatters de dinero/fechas, validaciones.
Específico de plataforma: componentes UI, acceso a hardware (impresora, cámara, USB), navegación, notificaciones push.

Sync con PowerSync + Supabase

PowerSync es la capa que convierte tu Supabase Postgres en una base de datos local por dispositivo, con sync automático. Es la pieza que hace el offline-first real — no un queue manual con reintentos.

Cómo funciona

Cada dispositivo tiene su copia de SQLite. PowerSync define qué tablas se sincronizan y a qué dispositivo (via RLS en Supabase). Las lecturas son siempre locales — sin latencia. Las escrituras van a la cola local de PowerSync y se suben cuando hay red.

Por qué PowerSync sobre la alternativa manual

El sync queue manual que teníamos antes resuelve el "cómo subir" pero no resuelve conflictos, no sincroniza hacia abajo (cambios en la nube no bajan al dispositivo), y no tiene UI de estado de sync. PowerSync resuelve todo eso. Tiene tier gratuito hasta 3 usuarios y luego $39/mes — viable para un negocio.

Inventario con event sourcing

El problema del inventario en multi-terminal: terminal A vende 2 unidades mientras terminal B está offline. Cuando reconectan, ambas tienen stock = 4. El resultado correcto es stock = 2. Si guardas el stock como número, no puedes resolver esto.

La solución: guardar eventos, no el estado resultante.

-- En vez de: UPDATE products SET stock = 4 -- Guardar el evento: INSERT INTO inventory_events (product_id, delta, reason, terminal_id, created_at) VALUES ('uuid-producto', -2, 'sale', 'terminal-a', '2026-08-26T14:03:00') -- El stock actual es SIEMPRE: SELECT SUM(delta) FROM inventory_events WHERE product_id = ?

Con eventos, los conflictos desaparecen: terminal A restó 2, terminal B restó 1, resultado = −3 del stock inicial. Además obtienes un log de auditoría completo de quién vendió qué y cuándo.

Red local

Cuando las terminales están en el mismo WiFi, el desktop actúa como servidor local. No se necesita internet para que el negocio opere.

Descubrimiento automático con mDNS

El proceso main de Electron anuncia el servicio en la red local con bonjour-service. Los dispositivos en la misma red acceden via http://mi-pos.local:3847 sin necesidad de conocer la IP del equipo.

// apps/desktop/src/main/server/mdns.ts import Bonjour from 'bonjour-service' export function startDiscovery(port: number) { const bonjour = new Bonjour() bonjour.publish({ name: 'Mi POS', type: 'http', port }) return () => bonjour.unpublishAll() }

Token de sesión

Al arrancar el servidor, genera un UUID de sesión. El dispositivo móvil lo escanea via QR (o lo ingresa manualmente) la primera vez. Todas las peticiones posteriores incluyen ese token en el header. Sin token = 401.

Cuando la terminal móvil ya tiene PowerSync

En Fase 3, cuando el móvil tiene su propia copia de SQLite vía PowerSync, ya no necesita el Express server para operar — puede vender de forma completamente autónoma. El Express server queda solo para sincronización en tiempo real dentro de la red local cuando internet no está disponible.

Diferenciadores vs Square y Loyverse

Square y Loyverse son herramientas de propósito general. Este POS puede ser la herramienta específica para negocios de servicio en México y LatAm.

★ 1
Citas de AppointVa → Cobro directo
El cliente llega con una cita agendada. El POS la detecta automáticamente, carga el servicio en el carrito, y procesa el pago. Un flujo, cero reingreso de datos. Ningún POS gratuito hace esto. Es el diferenciador del producto.
★ 2
Ticket por WhatsApp o QR digital
90%+ de penetración de WhatsApp en el mercado objetivo. Enviar el ticket como mensaje con el resumen de la compra elimina la impresión para clientes que no la quieren. El QR code en pantalla permite que el cliente lo guarde desde su celular.
★ 3
Indicador de sync honesto y visible
Un chip permanente: En línea — sync al día o Sin internet — 3 ventas en cola. Los cajeros saben exactamente qué está pasando. Square lo oculta. Loyverse lo oculta. La transparencia genera confianza en el sistema.
★ 4
Órdenes en pausa con nombre (parked orders)
Guardar una orden con un nombre ("Mesa 3", "Juan M.") y abrir una nueva mientras el cliente decide. Loyverse lo tiene parcialmente. Square no en el tier gratuito. Para salones, restaurantes pequeños, y tiendas con múltiples clientes simultáneos es esencial.
★ 5
Corte de caja profundo (Z-Report)
No solo el total del día — desglose por cajero, por método de pago, conteo físico de efectivo vs esperado, log de discrepancias, retiros de caja durante el turno. Las herramientas gratuitas tratan esto como un afterthought. Para el dueño del negocio, el corte de caja diario es su control más importante.
★ 6
Split payment (efectivo + tarjeta en una sola venta)
Extremadamente común en LatAm: el cliente paga $300 con tarjeta y $150 en efectivo. Square lo tiene. Loyverse gratuito no. Implementarlo desde el principio es más fácil que agregar después — el schema de payments ya lo soporta (N pagos por orden).

UX de alta velocidad

En un POS la velocidad es la feature. Cada segundo en el checkout importa cuando hay fila. Estas son las decisiones de diseño que separan un POS bueno de uno excelente.

Checkout
Grid de productos sobre lista
Tiles con imagen y precio. El cajero toca, no busca. La lista es para búsqueda de catálogos grandes. El grid es para lo que vende más el 80% de las veces.
Búsqueda
Búsqueda instantánea con Command
Atajo ⌘K / Ctrl+K en desktop abre el buscador. Primeras letras del nombre del producto. No hay que navegar por categorías.
Teclado
Shortcuts en desktop
F1 nuevo ticket · F2 buscar producto · F4 cobrar · Esc cancelar. Un cajero entrenado no toca el mouse.
Cantidades
Teclado numérico propio
No usar el teclado del sistema operativo para cantidades y montos. Un keypad custom en pantalla evita el layout del teclado virtual que tape la UI en mobile.
Feedback
Confirmación sonora opcional
Beep al agregar producto. Sonido de caja al completar pago. El cajero sabe que el tap registró sin mirar la pantalla. Toast visual + sonido.
Sin red
Chip de sync siempre visible
Un indicador pequeño, siempre en pantalla: verde = sincronizado, naranja = N ventas en cola. El cajero nunca se pregunta si el sistema "se cayó".
Errores
Sin errores bloqueantes en offline
El POS nunca muestra "Error de conexión" y bloquea el checkout. La falta de red es transparente para el cajero. Solo el chip de sync cambia de color.
Variantes
Bottom sheet, no pantalla nueva
Al tocar un producto con variantes, un bottom sheet aparece con las opciones (S/M/L, colores). El cajero elige y regresa al carrito. Sin navegar fuera del checkout.

Bases — lecciones aprendidas

Estas son las convenciones que deben quedar escritas y acordadas en la Fase 0, antes de cualquier feature. No son opiniones — son correcciones directas a bugs reales que costaron horas de debugging en proyectos anteriores.

Origen de estas reglas

Cada punto tiene una causa concreta. Un bug de timezone en un sistema de recordatorios. Un campo nuevo que requirió actualizar 5 archivos distintos y falló en producción porque faltó uno. Una variable declarada dentro de un bloque if usada afuera. Estas reglas existen para no repetir esos errores.

1. Todos los timestamps en UTC — sin excepción

Guardar fechas como hora local es la fuente de bugs más difíciles de reproducir en un sistema. El POS opera en México, los servidores de Supabase están en otra zona horaria, PowerSync tiene su propio timestamp. Si cada capa usa una referencia distinta, eventualmente algo falla de manera intermitente.

La regla: toda fecha se guarda como string ISO 8601 en UTC ("2026-08-26T20:30:00Z"). La conversión a hora local de México (America/Mexico_City) ocurre solo en la capa de presentación, al momento de mostrar en pantalla, usando date-fns con la zona horaria del dispositivo.

// packages/core/dates.ts — la única función que convierte a local import { format, toZonedTime } from 'date-fns-tz' const MX_TZ = 'America/Mexico_City' export function toMxDisplay(utcIso: string, fmt = 'dd/MM/yyyy HH:mm') { return format(toZonedTime(new Date(utcIso), MX_TZ), fmt, { timeZone: MX_TZ }) } // Al guardar — siempre: const created_at = new Date().toISOString() // UTC // Al mostrar — siempre a través de toMxDisplay() // NUNCA: new Date().toLocaleString() — depende del locale del dispositivo

2. Drizzle schema como fuente única de verdad

En AppointVa, agregar un campo nuevo requería actualizar el modelo C#, dos DTOs, dos interfaces TypeScript, y el mock de los tests. Faltar uno producía un error de build en producción. En el POS esto no puede pasar.

La regla: el schema de Drizzle en packages/db-schema/schema.ts es la única definición. Los tipos de TypeScript se infieren automáticamente — nunca se escriben a mano.

// packages/db-schema/schema.ts export const products = sqliteTable('products', { id: text('id').primaryKey(), name: text('name').notNull(), price: integer('price').notNull(), // centavos categoryId: text('category_id'), trackStock: integer('track_stock').default(1), active: integer('active').default(1), updatedAt: text('updated_at').notNull(), }) // Los tipos salen solos — nunca se definen por separado: export type Product = typeof products.$inferSelect export type NewProduct = typeof products.$inferInsert // Ahora Product y NewProduct son el contrato en toda la app. // Si agregas un campo al schema, TypeScript señala dónde falta manejarlo.
Por qué esto evita el bug de "5 archivos"

Cuando agregas hasVariants: integer('has_variants').default(0) al schema, TypeScript inmediatamente marca como error cada lugar donde construyes un objeto Product sin ese campo. No se puede olvidar actualizarlo — el compilador no deja pasar el build.

3. Validación Zod en cada frontera del sistema

TypeScript solo existe en tiempo de compilación. En runtime, los datos que llegan del IPC de Electron, de Supabase, o de PowerSync son unknown. Si asumes que tienen la forma correcta y no la tienen, obtienes crashes silenciosos o, peor, datos corruptos guardados en SQLite.

// packages/core/schemas.ts import { z } from 'zod' export const ProductSchema = z.object({ id: z.string().uuid(), name: z.string().min(1), price: z.number().int().positive(), // centavos, siempre entero positivo categoryId: z.string().uuid().nullable(), trackStock: z.number().int().min(0).max(1), active: z.number().int().min(0).max(1), updatedAt: z.string().datetime({ offset: true }), // ISO UTC obligatorio }) // En el handler IPC del proceso main de Electron: ipcMain.handle('products:create', async (_, raw) => { const data = ProductSchema.parse(raw) // lanza ZodError si algo está mal return db.insert(products).values(data) })

4. Migraciones de SQLite corren en el arranque de la app

El POS se instala en equipos del cliente y se actualiza. Cada actualización puede traer cambios de schema. Si las migraciones no corren automáticamente al abrir la app, el equipo del cliente trabaja con un schema viejo y los datos no coinciden con el código nuevo.

// apps/desktop/src/main/db/migrate.ts import { migrate } from 'drizzle-orm/better-sqlite3/migrator' import { db } from './client' export function runMigrations() { // Corre en el arranque, antes de que cualquier ventana abra migrate(db, { migrationsFolder: './drizzle/migrations' }) console.log('Migrations OK') } // apps/desktop/src/main/index.ts app.whenReady().then(() => { runMigrations() // primero las migraciones createWindow() // luego la ventana })

5. El IPC de Electron tiene un contrato TypeScript explícito

El proceso main y el renderer de Electron son procesos separados. Si expones una función en el preload y después cambias su firma en el main, el renderer recibe undefined sin error visible. Este tipo de bug es especialmente difícil de rastrear.

// packages/core/ipc-contract.ts — definido UNA sola vez export interface PosAPI { products: { list: () => Promise<Product[]> create: (data: NewProduct) => Promise<Product> update: (id: string, data: Partial<Product>) => Promise<Product> } orders: { create: (data: CreateOrderInput) => Promise<Order> today: () => Promise<Order[]> } printing: { ticket: (orderId: string) => Promise<void> } } // preload/index.ts usa este tipo → el renderer también lo usa // Si no coinciden, TypeScript lo detecta antes de compilar

6. Variables declaradas en el scope donde se usan

Regla simple: nunca declarar una variable dentro de un bloque if, try, o for si se va a usar fuera de él. En TypeScript esto es un error de compilación. En el proceso main de Electron (Node.js puro) también. Pero si la lógica es compleja, la solución es extraer la lógica a una función, no usar una variable con alcance más amplio.

// MAL — tz queda atrapado en el if: if (condicion) { const tz = resolverZonaHoraria() } // tz no existe aquí — error en runtime // BIEN — declarar antes o extraer a función: const tz = condicion ? resolverZonaHoraria() : DEFAULT_TZ // o mejor aún, extraer toda la lógica a una función pura

7. EAS Build configurado desde la Fase 0

El error más caro en Expo es descubrir que la app no compila para iOS cuando ya tienes 8 semanas de features. Los módulos nativos (react-native-esc-pos-printer, react-native-vision-camera) requieren un build nativo — no funcionan en Expo Go. Si no pruebas el build real desde el principio, encuentras problemas de compilación cuando ya hay mucho código encima.

# Configurar en Fase 0, no en Fase 3: npm install -g eas-cli eas login eas build:configure # Primer build de desarrollo — con los módulos nativos del día 0: eas build --profile development --platform android # Esto genera un .apk que puedes instalar en tu celular y conectar al Metro bundler

8. Tests para packages/core desde el primer día

La lógica en packages/core — cálculo de carrito, split payment, cambio en efectivo, event sourcing de inventario — son funciones puras sin dependencias de UI ni de base de datos. Son triviales de testear y críticas de que funcionen correctamente. Un error en el cálculo de cambio en un POS es un problema real para el negocio.

// packages/core/cart.test.ts import { calcChange, applyDiscount } from './cart' test('calcChange regresa el cambio correcto', () => { expect(calcChange(15000, 20000)).toBe(5000) // centavos }) test('applyDiscount percent no puede dar negativo', () => { expect(applyDiscount(10000, { type: 'percent', amount: 110 })).toBe(0) }) test('split payment suma igual al total', () => { const payments = [{ amount: 8000 }, { amount: 7000 }] expect(payments.reduce((s, p) => s + p.amount, 0)).toBe(15000) })

9. Error boundaries — el POS nunca crashea completamente

Un error de JavaScript no capturado en el renderer de Electron o en React Native puede tumbar toda la pantalla de ventas en medio de una transacción. Los React Error Boundaries atrapan errores y muestran una pantalla de recuperación en lugar de un crash blanco.

// apps/desktop/src/renderer/POSErrorBoundary.tsx export class POSErrorBoundary extends React.Component { state = { hasError: false, error: null } static getDerivedStateFromError(error) { return { hasError: true, error } } render() { if (this.state.hasError) return ( <div className="flex flex-col items-center justify-center h-screen gap-4"> <p className="text-xl font-semibold">Algo salió mal</p> <p className="text-sm text-slate-500">{this.state.error?.message}</p> <button onClick={() => this.setState({ hasError: false })}> Reintentar </button> </div> ) return this.props.children } }

Setup inicial del monorepo

Crear el monorepo con Turborepo

npx create-turbo@latest mi-pos --package-manager pnpm cd mi-pos

Crear la app desktop (Electron)

cd apps npm create @quick-start/electron@latest desktop -- --template react-ts cd desktop pnpm install

Crear la app móvil (Expo)

cd apps npx create-expo-app@latest mobile --template tabs cd mobile npx expo install expo-router expo-sqlite expo-camera pnpm add nativewind tailwindcss pnpm add -D @expo/metro-config

Crear los packages compartidos

mkdir -p packages/{core,db-schema,store,api,sync,config} # Cada uno necesita su package.json con name "@pos/[nombre]" # y tsconfig.json que extiende packages/config/tsconfig.base.json

tsconfig base compartido

// packages/config/tsconfig.base.json { "compilerOptions": { "strict": true, "target": "ES2022", "module": "ESNext", "moduleResolution": "bundler", "skipLibCheck": true, "paths": { "@pos/core": ["../../packages/core/src"], "@pos/db-schema": ["../../packages/db-schema/src"], "@pos/store": ["../../packages/store/src"], "@pos/api": ["../../packages/api/src"], "@pos/sync": ["../../packages/sync/src"] } } }

pnpm-workspace.yaml

packages: - 'apps/*' - 'packages/*'

Instalar dependencias de cada capa

# En packages/db-schema: pnpm add drizzle-orm pnpm add -D drizzle-kit # En apps/desktop (además de lo de electron-vite): pnpm add better-sqlite3 express bonjour-service pnpm add receipt-printer-encoder @node-escpos/usb-adapter pnpm add -D @types/better-sqlite3 @types/express # En apps/mobile: pnpm add react-native-esc-pos-printer pnpm add react-native-vision-camera # barcode scanning pnpm add @powersync/react-native # En packages/sync: pnpm add @powersync/common # En packages/store: pnpm add zustand # En packages/api: pnpm add @supabase/supabase-js # En apps/desktop renderer: pnpm add tailwindcss @tailwindcss/vite npx shadcn@latest init
